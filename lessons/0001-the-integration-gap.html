Lesson 1: The Integration Gap

To integrate with opencode, your server must do more than just "return text". opencode is an autonomous agent; it uses the LLM as a reasoning engine to decide which tools to call, read their output, and iterate until a task is complete.

The "A-ha" Moment

Current Server: A Chat Gateway. It takes a prompt $\to$ returns a string.

opencode Requirements: An Agent Gateway. It takes a state (messages + tools) $\to$ returns a decision (content OR tool calls).

The Gap Analysis

Based on the audit of server/api.py and copilot/providers/base.py, here are the critical missing pieces:

Tool Calling The server ignores the tools field in requests. It cannot receive or process tool_calls from the LLM, meaning opencode cannot actually use any of its capabilities (bash, read, edit) through your server.
State Loss The AbstractProvider interface accepts a prompt: str. This destroys the message history and structure required for complex agentic loops. We need to pass the full List[ChatMessage].
Blind Models /v1/models returns basic IDs. opencode needs to know if a model supports tool calling and what its context window is to avoid truncation during long coding sessions.
SSE Simplicity The streaming implementation is basic. High-end agent SDKs (like Vercel AI SDK) expect usage metadata and specific finish_reason values (e.g., tool_calls) to manage the loop.

Your First Tangible Win

The Blueprint

The first step to fixing this is redefining the core contract. We must change the AbstractProvider from:

def chat(self, prompt: str, ...)

to:

def chat(self, messages: List[ChatMessage], tools: List[Tool], ...)

This single change unlocks the ability to support everything an agent needs.

Deep Dive

To understand exactly what opencode is sending, read the Vercel AI SDK OpenAI Compatible spec. This is the "truth" we are targeting.
