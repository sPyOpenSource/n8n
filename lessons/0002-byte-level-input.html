Byte-Level Input

Lesson 2 · Raw UTF-8 bytes as language model tokens

Why This Matters

In Lesson 1, we built a Markov model to generate synthetic stories fast. But there's another speed lever: how the SLM itself reads text.

Most language models use BPE tokenization — a learned vocabulary of subword units (e.g., 4,096 tokens). This requires training and shipping a separate tokenizer. The alternative is byte-level input: every raw UTF-8 byte (0–255) is its own token. No tokenizer needed. Vocab is fixed at 256.

This matters for your mission because byte-level input simplifies the entire pipeline — `prepare.py` drops the tokenizer entirely, and `train.py` becomes smaller and faster to train per step.

The Core Idea

Byte-level means no tokenization at all. You take the raw bytes of a text file and feed them directly to the model:

"Cat" → UTF-8 bytes → [67, 97, 116] → token IDs [67, 97, 116]

The embedding layer (wte) maps each byte value 0–255 to an embedding vector, just like it would map a BPE token ID. The rest of the model (attention, MLP, LM head) is unchanged — it just sees more, smaller tokens.

Byte-Level vs BPE

Aspect Byte-Level BPE (4,096)
Vocab size 256 (fixed) 4,096 (trained)
Tokenizer needed? No Yes — train + save + load
Tokens per word ~3–5 (one per byte) ~1–2 (subword units)
Unicode coverage Universal — any UTF-8 works Limited — unknown bytes → UNK
What model learns Characters → words → grammar from scratch Subword patterns are pre-defined

The Trade-Off

Byte-level sequences are longer — a 5-word story might be 50+ bytes instead of 10–15 BPE tokens. This means more compute per story. But each step is cheaper (smaller embedding table), and you skip tokenizer overhead entirely.

In our experiments on Apple Silicon:

Setup val_bpb Steps (5 min) tok/sec VRAM
BPE (vocab=4,096) 1.592583 83 ~9,600 3.8 GB
Byte-level (vocab=256) 1.922753 203 ~22,000 2.0 GB

The byte-level model fits 2.4× more steps into the same 5-minute budget, uses 47% less memory, but has a higher val_bpb because it must learn word structure from raw bytes. For small models on memory-constrained hardware, byte-level is often the better trade-off.

What Changes in the Code

prepare.py: Remove rustbpe, tiktoken, the Tokenizer class, and `train_tokenizer()`. Replace with a simple text.encode("utf-8") → list of ints. `make_dataloader` no longer takes a tokenizer argument.

train.py: Set `vocab_size = 256`. Remove the `Tokenizer` import and instantiation. `make_dataloader(batch_size, MAX_SEQ_LEN, "train")` — no tokenizer arg. `evaluate_bpb(model, batch_size)` — no tokenizer needed; every target byte has length 1.

Exercise: Convert a String to Byte Tokens

Your turn. Write a function that converts text to byte-level token IDs and back. Then test it on a TinyStories sentence.

  1. Encode "Hello, world!" to UTF-8 bytes
    2. Verify each value is 0–255
  2. Decode the bytes back to text Verify roundtrip: decode(encode(s)) == s

Run this to test:

text = "Hello, world!"
byte_tokens = list(text.encode("utf-8"))
print(f"Tokens: {byte_tokens}")
print(f"Count: {len(byte_tokens)} tokens (vs ~3 BPE tokens)")
print(f"Range: {min(byte_tokens)}–{max(byte_tokens)}")

# Roundtrip
decoded = bytes(byte_tokens).decode("utf-8")
print(f"Roundtrip OK: {decoded == text}")

# What a BPE tokenizer might produce instead:
# "Hello" → [15496], "," → [11], " world" → [2789], "!" → [0]
# Total: 4 tokens vs 13 byte tokens
