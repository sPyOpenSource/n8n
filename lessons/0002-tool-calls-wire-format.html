Lesson 2: The Tool Calling Protocol

How opencode gives the LLM "hands" to act on your codebase.

In Lesson 1, we identified that opencode uses Tool Calling to make decisions. Now we need to understand exactly how that works on the wire.

The OpenAI Chat Completions API has a simple extension for this: the tools parameter. But the streaming format for tool calls is complex and error-prone to implement incorrectly.

1. How opencode Uses Tools

Every time opencode sends a chat request, it includes a tools array. This array defines the actions opencode wants the LLM to be able to take:

tools = [
  {
    "type": "function",
    "function": {
      "name": "read_file",
      "description": "Read a file from the filesystem",
      "parameters": { ... }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "bash",
      "description": "Run a shell command",
      "parameters": { ... }
    }
  },
  {
    "type": "function",
    "function": {
      "name": "edit",
      "description": "Edit a file with a diff",
      "parameters": { ... }
    }
  }
]

Without this array, the LLM cannot invoke any of opencode's capabilities. Your server must pass tools through to the underlying model and process tool_calls in the response.

2. The Decision Point

When the model receives the tools, it has two options:

Option A: Answer normally — The model returns finish_reason: "stop" and content: "text...". This means the task is complete or the model is clarifying.

Option B: Call a tool — The model returns finish_reason: "tool_calls" and tool_calls: [...] with no content.

Your server must distinguish between these two cases. This is done by checking finish_reason in the response.

3. The Streaming Challenge

In streaming mode, tool calls arrive as incremental deltas. A single tool call like {"path": "/main.py"} might arrive as 20 separate chunks. The Vercel AI SDK reconstructs these, but only if the format is exact:

// Chunk 1: declare the tool call
data: {"choices":[{"index":0,"delta":{"role":"assistant","tool_calls":[{"index":0,"id":"call_xxx","type":"function","function":{"name":"read_file","arguments":""}}]}}]}

// Chunks 2..N: stream the arguments
data: {"choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\""}}]}}]}
data: {"choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"function":{"arguments":"path\\\":"}}]}}]}
// ... more chunks ...

// Final chunk: signal completion
data: {"choices":[{"index":0,"delta":{},"finish_reason":"tool_calls"}]}
data: [DONE]
Common Mistake: Sending finish_reason: "tool_calls" on the wrong chunk, or omitting the index field inside tool_calls. The SDK uses index to group partial arguments belonging to the same tool call.

4. The Tool Call Loop

After the model returns tool_calls, the "agent" loop happens outside your server:

  1. opencode receives the tool_calls response from your server
  2. opencode executes the tools (reads files, runs bash)
  3. opencode sends a new request with role: "tool" messages containing the results
  4. Your server forwards these to the model so it can reason about the results
  5. Rinse and repeat until the model responds with finish_reason: "stop"

5. How Your Server Fails Today

server/schemas.py No tools or tool_choice fields in ChatCompletionRequest
server/openai_format.py completion_response always returns a static message with content, never tool_calls
copilot/providers/base.py AbstractProvider accepts a prompt: str, not messages + tools
Your Tangible Win

You can now read the tool calling protocol. If you see a JSON response with tool_calls inside choices[0].message, you know exactly what's happening.

This is a skill called "wire format literacy" — the ability to look at raw API traffic and understand the agentic loop.
