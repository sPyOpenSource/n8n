Byte-Level Input

Reference — raw UTF-8 bytes as language model tokens. See Lesson 2.

Core Idea

Instead of tokenizing text into subword units (BPE, WordPiece, etc.), a byte-level model treats every raw UTF-8 byte (0–255) as a separate token. The vocabulary is fixed at 256 — one token per possible byte value.

Byte-Level vs BPE Tokenization

Aspect Byte-Level BPE (e.g., 4096)
Vocab size 256 (fixed) 4,096+ (trained)
Tokenizer needed? No Yes — must train & ship
Sequence length Longer (~3-4× more tokens per word) Shorter
Unicode support Universal — any UTF-8 text works Limited to training vocab
What model learns Characters → words → grammar from scratch Subword patterns are pre-defined

How It Works

Encoding:
"Hi" → bytes [72, 105] → token IDs [72, 105]

Embedding:
wte.weight[72] → 384-dim vector for 'H'
wte.weight[105] → 384-dim vector for 'i'

Implementation Changes

  • prepare.py: Remove rustbpe, tiktoken, Tokenizer class. Replace with text.encode("utf-8") → list of ints (0–255).
  • train.py: Set vocab_size = 256. Remove Tokenizer import and instantiation. make_dataloader(batch_size, seq_len, split) — no tokenizer arg.
  • evaluate_bpb: Every target token is a byte (byte length = 1). No token_bytes lookup needed.

Trade-Offs

Advantage Disadvantage
No tokenizer to train, save, or version 3-4× longer sequences — more compute per story
Smaller embedding table (256 vs 4,096) Model must learn word boundaries from scratch
Handles any Unicode without UNK tokens Higher val_bpb initially (model has more to learn)

Experimental Results (Apple Silicon, 5-min budget)

Setup val_bpb Steps tok/sec VRAM
BPE (vocab=4,096) 1.592583 83 ~9,600 3.8 GB
Byte-level (vocab=256) 1.922753 203 ~22,000 2.0 GB
